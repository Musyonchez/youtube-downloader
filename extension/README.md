# YT MP3 Queue -- Chrome extension

A Manifest V3 Chrome extension that adds a floating **"Send to MP3
Queue"** button on YouTube video and playlist pages. Clicking it adds the
current video (or every not-yet-queued video in the current playlist) to
this app's library queue -- the same effect as pasting the link into the
web app's own "paste a link" search mode, just without leaving YouTube.

It does **not** start a download. It only queues. Downloads still start
from the web app itself, same as always.

It reuses your existing logged-in session on the deployed app (via the
session cookie) -- there is no separate login inside the extension. If
you're not logged in, the button (and the popup) tell you so and offer a
one-click link to `/login`.

## Thumbnail badges

On top of the floating button (which only appears on `/watch` and
`/playlist` pages), a small status badge is drawn in the top-left corner of
**every video thumbnail on any youtube.com page** -- home feed, search
results, channel pages, sidebars/related videos, subscriptions, playlist
listings. Three states:

- **New** (copper `+`) -- clickable. One click queues the video immediately,
  right from the thumbnail, without opening it.
- **Queued** (teal hourglass) -- already in the library queue, not yet
  downloaded. Indicator only, not clickable -- clicks pass through to
  YouTube's own thumbnail link so the page still navigates normally.
- **Downloaded** (green check) -- already in download history. Also
  indicator-only.

This is the whole point of the badges: not having to open a video first
just to queue it. YouTube Shorts thumbnails are explicitly skipped (out of
scope, different DOM shape).

Clicking a "new" badge shows a toast in the bottom-left corner with the
video's title and an **Undo** button (auto-dismisses after 10 seconds;
stacks up to 5 toasts, oldest dropped first if a 6th arrives). Undo removes
the video from the queue and reverts the badge to "new" in place.

Badge status is resolved via a batched `POST /api/statuses` call (added
alongside this feature -- see `app/api/routes.py`) rather than one
`/api/video-info` call per thumbnail, which would be far too slow given a
page can have hundreds of thumbnails; that endpoint is a pure-DB lookup,
never touches yt-dlp. Newly-seen thumbnails are collected via a debounced
`MutationObserver` (YouTube is a SPA with infinite scroll/lazy loading) and
resolved in one batch per ~350ms window; resolved statuses are cached
in-memory per page load and only ever corrected by this extension's own
actions (add / undo), never re-polled on a timer.

**A note on DOM fragility**: YouTube's frontend is a large, frequently
redeployed SPA, and live inspection while building this feature (2026-08)
found it mid-migration between two renderer generations *on the same
site* -- search results still use the older `ytd-video-renderer` /
`ytd-thumbnail` structure, while channel grids and the watch-page sidebar
have moved to a newer `yt-lockup-view-model` / `yt-thumbnail-view-model`
structure. `thumbnail_badges.js` targets both, plus the renderer tag names
this feature's task named (`ytd-compact-video-renderer`,
`ytd-grid-video-renderer`, `ytd-playlist-video-renderer`) even though live
inspection didn't turn up examples of those on the pages checked. This
worked as of the test run documented below, but there's no guarantee
YouTube's markup stays put -- if badges stop appearing on some layout in
the future, the DOM structure most likely shifted again and
`thumbnail_badges.js`'s selectors need a refresh, the same maintenance
reality `content.js`'s own comment already calls out for the floating
button.

## What's in here

- `manifest.json` -- MV3 manifest. Pins a stable extension ID via the
  `"key"` field (see "Stable extension ID" below).
- `background.js` -- service worker; the only place that talks to the
  API (see its top comment for why).
- `content.js` / `content.css` -- injected on every `youtube.com/*` page;
  renders the floating button (scoped internally to `/watch` and
  `/playlist` only).
- `thumbnail_badges.js` / `thumbnail_badges.css` -- injected on every
  `youtube.com/*` page; renders the thumbnail status badges and toast
  notifications described above.
- `popup/` -- the small popup shown when you click the toolbar icon
  (login status + a link to the web app).
- `common.js` -- shared constants (API base URL).
- `icons/` -- 16/48/128px PNGs, generated by `gen_icons.py` (Pillow).
- `gen_key.js` -- one-off script that generated the dev RSA keypair /
  computed the extension ID below. The private key it produces
  (`dev_private_key.pem`) is gitignored and never committed.

## Loading it for development

1. `chrome://extensions`
2. Enable **Developer mode** (top-right toggle).
3. **Load unpacked** → select this `extension/` directory.
4. Visit any `youtube.com/watch?v=...` or `youtube.com/playlist?list=...`
   page -- the floating button should appear bottom-right within a moment.

Because `manifest.json` embeds a `"key"` field, Chrome derives the
extension's ID from that key rather than from the folder's filesystem
path -- so the ID stays the same (`lfcekljajioeijjmcaandpbdlgddlmda`, see
below) no matter where you check this repo out or move it. That matters
here specifically because the backend's CORS allowlist trusts one exact
`chrome-extension://<id>` origin -- if the ID could drift, the backend
would have to trust either a wildcard (defeats the point) or a
long-lived guess.

## Stable extension ID

Chrome computes an unpacked extension's ID from the SHA-256 hash of the
DER-encoded `SubjectPublicKeyInfo` of the key in `manifest.json`'s
`"key"` field: take the first 16 bytes of that hash, then map each nibble
(0-15) to a letter `a`-`p` (0→a, 1→b, ..., 15→p). That's exactly what
`gen_key.js` does after generating a 2048-bit RSA keypair with Node's
built-in `crypto` module.

For this repo's dev keypair, that works out to:

```
chrome-extension://lfcekljajioeijjmcaandpbdlgddlmda
```

which is the exact origin `app/main.py`'s `EXTENSION_ORIGIN` constant
allowlists in CORS. **If you regenerate the keypair** (`node
gen_key.js`), you'll get a different ID and origin -- you must update
`EXTENSION_ORIGIN` in `app/main.py` to match, or every request from the
extension will fail CORS with no cookie ever sent (the browser blocks it
client-side before the request even reaches the network in a readable
way -- it shows up as an opaque "Failed to fetch" / CORS console error,
not an HTTP error status).

## The CORS / cookie mechanism

This is the actual hard part of this extension, and worth spelling out.

The backend's session cookie is `SameSite=Lax`, and CORS used to be
`allow_origins=["*"]` + `allow_credentials=False` -- both deliberately
set up (see `app/main.py`'s comments, docs/16 finding 16-22/E-3) so that
**no** cross-origin request, from anywhere, could ever ride along with
the session cookie. That's a real CSRF mitigation and it was never going
to be safe to just weaken it globally for every client to unblock this
one extension.

What actually changed, scoped as tightly as possible:

1. **CORS allowlist narrowed, not widened.** `allow_origins` went from
   `["*"]` to a single explicit entry -- exactly
   `chrome-extension://lfcekljajioeijjmcaandpbdlgddlmda` (this
   extension's own origin, derived from the pinned key above) --
   alongside `allow_credentials=True`. `allow_credentials=True` +
   wildcard origins is a combination the CORS spec forbids browsers from
   honoring anyway, so the wildcard had to go regardless of what replaced
   it; narrowing it to one real origin is strictly *tighter* than before
   for every caller that isn't this extension (a same-origin browser tab
   was never subject to CORS in the first place -- CORS only applies to
   cross-origin requests).
2. **A real bug this surfaced and fixed along the way:**
   `SessionAuthMiddleware` (which gates `/api/*` behind a valid session)
   runs *before* `CORSMiddleware` in the ASGI stack (see
   `app/session_auth.py`'s module docstring on middleware ordering).
   Browsers never attach cookies to a CORS *preflight* (`OPTIONS`)
   request, credentialed or not -- only to the real request that follows
   a successful preflight. That means every preflight would hit
   `SessionAuthMiddleware` looking "logged out", get a bare 401 with no
   CORS headers on it, and the browser would abort the whole request
   right there -- the real, cookie-carrying request would never even be
   sent. `SessionAuthMiddleware` now lets `OPTIONS` requests through
   unauthenticated so `CORSMiddleware` (further in) can actually answer
   the preflight. See `tests/test_auth_routes.py`'s
   `test_cors_allows_extension_origin_with_credentials` -- it caught this
   exact failure before it ever reached a browser.
3. **Which mechanism actually carries the cookie:** `fetch(url,
   {credentials: 'include'})` from this extension's background service
   worker, verified live against the real deployed app (see "Testing"
   below) -- **not** the `chrome.cookies` + `declarativeNetRequest`
   cookie-injection fallback described as a contingency in this feature's
   original plan. Chrome's `SameSite=Lax` enforcement exists to stop a
   third-party *web page* from riding a user's cookies to another site;
   a request whose initiator is this extension's own
   `chrome-extension://<id>` origin isn't the kind of cross-site request
   that protection is aimed at, and empirically Chrome does not withhold
   the cookie here once the origin is CORS-allowlisted with credentials.
   Because the simple path worked, the `declarativeNetRequest` fallback
   was never implemented -- `manifest.json` does not request the
   `declarativeNetRequest` permission, only `cookies` (unused today, kept
   as the documented fallback point if a future Chrome version changes
   this behavior) and `storage`.

If a future Chrome release ever tightens this further and the cookie
stops riding along, the fallback path is: `chrome.cookies.get()` to read
the session cookie's value directly (not subject to `SameSite`
restrictions), then `chrome.declarativeNetRequest` dynamic rules to
inject a `Cookie:` header onto the outgoing request (`fetch()` cannot set
`Cookie` directly -- it's a forbidden header name). That fallback is
*not* currently implemented because it wasn't needed.

## Testing

- **Backend**: `pytest tests/`, `ruff check`, `mypy app/` -- same as
  always, run from the repo root. The CORS change added
  `test_cors_allows_extension_origin_with_credentials` and
  `test_cors_rejects_arbitrary_third_party_origin` to
  `tests/test_auth_routes.py`.
- **Extension, live**: `tests/e2e/extension_live_test.js` (`node
  extension_live_test.js` from `tests/e2e/`, after `npm install` +
  `npx playwright install chromium` there) drives this against the actual
  deployed app (`https://yt-mp3-downloader.fly.dev`) using Playwright's
  `launchPersistentContext` with `--load-extension`/
  `--disable-extensions-except` pointed at this directory (MV3 extensions
  need a headed, non-headless launch to run their service worker in this
  Playwright/Chromium combination).
  - A first persistent context logs in for real (`musyonchez` /
    the live admin password) and navigates to
    `youtube.com/watch?v=jNQXAC9IVRw` ("Me at the zoo", the first video
    ever uploaded to YouTube -- picked for long-term stability). The
    floating button correctly resolved to "Send to MP3 Queue" (i.e.
    `/api/video-info` succeeded with the cookie attached, not a 401),
    clicking it resolved to "Added! ✓", and a follow-up first-party
    `GET /api/library` from the same context confirmed the video was
    genuinely present server-side -- not just an optimistic UI state.
  - A second, fresh/never-logged-in persistent context on the same page
    correctly rendered "Not logged in — click to log in", and clicking it
    opened `/login` in a new tab.
  - The video added during the first run was removed afterward via
    `DELETE /api/library/{video_id}` (verified gone with a follow-up
    `GET /api/library`); `/api/download` was never called.
  - Actual output from the run that verified this (also see "The CORS /
